# 왜 NetBird인가 — 보안 설계와 근거

이 문서는 "무엇을 어떻게 설치하는가"가 아니라 **"왜 이런 구조를 골랐는가"**를 남긴다.
설치 절차는 [../README.md](../README.md)를 볼 것.

## 목표

**공인 인터넷에 노출되는 포트를 최소화한다.**

우리는 고객 주민등록번호를 포함한 고유식별정보를 취급한다. 인터넷에 열어둔 포트 하나하나가
전 세계 스캐너와 봇의 상시 표적이고, 그 뒤에 있는 소프트웨어에 취약점이 발견되는 순간
곧바로 위험이 된다. 열어둔 문이 적을수록 지켜야 할 곳도 적다.

## 계기

사무원들이 윈도우 탐색기로 웹드라이브를 쓰게 해달라는 요구에서 시작했다.

이를 위해 drive에 SFTP 서버를 구현했는데, 문제는 **SFTP가 HTTP가 아니라는 점**이다.
게이트웨이(Spring Cloud Gateway)는 HTTP 요청만 라우팅하므로 SSH 기반 SFTP를 프록시할 수 없다.
결국 drive가 자체 포트(38592)를 공인망에 직접 열어야 한다는 결론이 나왔다.

여기서 질문이 뒤집혔다. **"이 포트를 열까"가 아니라 "이런 포트를 계속 늘려도 되는가".**

## 이전 구조의 문제

```
인터넷 ──→ 443    (gateway, 고객용 웹/API)
       ──→ 38592  (drive SFTP)          ← 신규 요구
       ──→ ????   (Databasus DB 백업 툴) ← 다음 요구
       ──→ ????   (그다음 내부 도구)
```

내부 인원만 쓰는 도구인데도 **전 세계에 열어야** 한다. 서비스가 늘 때마다 문이 하나씩 늘고,
각 문 뒤의 소프트웨어를 전부 최신으로 유지해야 한다.

특히 SFTP는 위험도가 높다. Apache MINA SSHD가 인터넷에 그대로 노출되고,
그 구현에 취약점이 나오면 인증 이전 단계에서 뚫릴 수 있다. 무차별 대입도 상시 들어온다.

## NetBird 구조

```
인터넷 ──→ 443/TCP, 3478/UDP  (NetBird 관리서버) ← 노출은 여기 하나뿐

           그 외 모든 서비스는 인터넷에서 보이지 않음
           drive SFTP · Databasus · 앞으로 추가될 것들
```

서비스가 열 개로 늘어도 **인터넷에 노출되는 건 여전히 관리서버 하나**다.
지켜야 할 문이 N개에서 1개로 줄어든다. 이것이 이 구조의 핵심 이득이다.

## 왜 포트를 안 열어도 서로 통신이 되는가

가장 헷갈리는 지점이다. peer끼리 직접 통신한다면서 왜 인바운드 포트가 필요 없는가?

**UDP 홀 펀칭** 덕분이다.

```
[윈도우 PC]                                  [swarm-manager]
 인바운드 0개                                   인바운드 0개
     │                                             │
     │ ① 아웃바운드로 STUN(3478)에 접속               │
     └──────────────→ [관리서버] ←──────────────────┘
                          │
             ② 서로에게 상대 주소를 알려줌
                          │
     ┌────────────────────┴─────────────────────┐
     │ ③ 양쪽이 동시에 상대에게 아웃바운드 발신       │
     └──────────────────────────────────────────┘
     ④ NAT가 "내가 보낸 곳에서 온 응답"으로 인식해 통과
     ⑤ 터널 성립 → 이후 직접 통신
```

방화벽은 원래 "내가 먼저 말을 건 상대의 답장"은 통과시킨다. 그 성질을 이용하므로
**양쪽 모두 인바운드가 완전히 닫혀 있어도 연결된다.** 나가는 길만 있으면 된다.

그래서 stg 서버들은 인바운드 포트를 단 하나도 열지 않는다.

## 방어가 두 겹이다

이전에는 SFTP 로그인 하나만 뚫으면 끝이었다. 지금은 두 계층을 통과해야 한다.

| 계층 | 통과 조건 |
|---|---|
| 네트워크 | NetBird 망에 가입된 기기여야 함. 아니면 SFTP는 **존재 자체가 안 보임** |
| 신원 | Keycloak 계정 + 관리자 승인 + SFTP는 허용된 회사 소속일 것 |

포트 스캔을 해도 SFTP 포트는 잡히지 않는다. 공격자 입장에서 표적을 찾을 수 없다.

## 트래픽은 어디로 흐르는가

관리서버는 **교환원**이지 통로가 아니다.

```
[윈도우 PC]  ←── 직접 WireGuard 터널 ──→  [swarm-manager] → drive SFTP
      ╲                                      ╱
       ╲──── 제어 신호만 ──[관리서버]── 제어 신호만 ────╱
                (누구와 연결할지 알려줄 뿐)
```

SFTP로 1GB 파일을 올려도 관리서버는 그 데이터를 한 바이트도 보지 않는다.
peer끼리 직접 주고받는다. 그래서 관리서버가 병목이 되지 않고,
관리서버가 잠깐 죽어도 **이미 연결된 peer 간 통신은 유지된다**(신규 등록과 정책 변경만 막힌다).

또한 등록된 대역으로 가는 트래픽만 터널을 탄다. 일반 인터넷 사용(네이버, 유튜브)은
터널을 거치지 않고 기존 회선으로 그대로 나간다.

실제 라우팅 테이블이 이를 보여준다(swarm-manager).

```
default via 10.10.2.1 dev ens18     ← 기본 경로 그대로
100.105.0.0/16 dev wt0              ← NetBird 대역만 추가
```

## 정직한 한계

과장하지 않기 위해 남긴다.

### 엄밀히는 "443만"이 아니다

실제로 여는 포트는 둘이다.

| 포트 | 용도 |
|---|---|
| 443/TCP | 관리서버 (대시보드, peer 등록, 정책 배포) |
| 3478/UDP | STUN (홀 펀칭 ①단계 — 서로의 주소를 알아내는 용도) |

3478은 "네 주소는 이거야"를 알려주는 것 외에 아무 일도 하지 않는다. 데이터도 인증 정보도
흐르지 않는다. 그래도 열려 있는 포트는 열려 있는 포트이므로 사실대로 적어둔다.

### Relay를 타면 관리서버가 트래픽을 나른다

양쪽 NAT가 까다로워 P2P 직접 연결이 실패하면 중계(relay)를 경유한다. 이때는 관리서버가
실제 데이터를 통과시키므로 부하가 생긴다. **설정으로 막을 수 없고 상대 네트워크 환경에 달렸다.**

사무원 여러 명이 대용량 파일을 다루는데 전부 relay를 탄다면 관리서버가 병목이 된다.
`netbird status`로 P2P인지 relay인지 확인할 수 있다. relay 비중이 높으면 공유기에서
WireGuard 포트(51820/UDP)를 열어 직접 연결 성공률을 높이는 방법이 있다.

### 관리서버가 단일 장애점이다

지금 관리서버는 사무실 노트북 한 대다. Wi-Fi 전용이고 등록된 SSID가 하나뿐이다.
이 기계가 죽으면 신규 peer 등록과 정책 변경이 막힌다(기존 연결은 유지된다).

최후의 복구 경로는 **사무실 LAN에서 내부 IP로 직접 SSH**하는 것이다.
그래서 노트북을 사무실 밖으로 옮기면 안 된다.

## 운영할 때 지켜야 할 것

이 구조의 이점을 무너뜨리는 실수들이다.

- **등록하는 대역을 좁게 유지할 것.** `0.0.0.0/0` 같은 걸 리소스로 등록하면 exit node를
  켜지 않아도 모든 트래픽이 터널을 탄다. 이름만 다를 뿐 결과는 같다.
- **Exit Node 기능을 켜지 말 것.** 켤 이유가 없다.
- **신규 사용자 자동 승인을 켜지 말 것.** 켜면 Keycloak `biseo` realm에 계정이 있는
  사람은 누구나 VPN에 들어온다. 관리자가 한 명씩 승인하는 현재 방식이 맞다.
- **SSH 포트를 공인망에 열지 말 것.** 원격 관리가 필요하면 NetBird 자체를 쓰거나
  사무실 LAN에서 접근한다. 22번을 여는 순간 이 프로젝트의 목적이 무너진다.

## 왜 Tailscale이나 Headscale이 아닌가

| | 판단 |
|---|---|
| Tailscale | 컨트롤 플레인이 외부 SaaS에 있다. 트래픽 내용은 안전하지만 **디바이스 목록과 접근 통제 정보가 외부 업체 서버에 남는다.** 고유식별정보 취급 환경에서 감사 소명 부담이 된다 |
| Headscale | 공식 FAQ에서 스스로 *"Headscale is not enterprise software and our focus is homelabbers and self-hosters"*라고 밝히고 있다. 유지보수자도 본업이 따로 있는 개인 2명이다 |
| **NetBird** | 회사가 만들고 상업 지원이 존재하며, **self-host가 공식 1급 배포 경로**다. 컨트롤 플레인까지 전부 사내에 둘 수 있다 |

GitHub Star는 Headscale(42.8k)이 NetBird(28.3k)보다 많지만, 이슈 해결률은 NetBird 쪽이 낮다는
점보다 **프로젝트 스스로가 규정한 용도**가 결정적이었다. 취미용이라고 밝힌 프로젝트에
회사 인프라 전체의 접근 통제를 얹을 수는 없다.
